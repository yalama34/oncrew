# О проекте

OnCrew - это оркестратор AI-агентов, в котором пользователь передаёт задачу команде, и тимлид распределяет работу между воркерами и проверяет результаты.

Система позволяет:

- Создавать агентов с разными ролями и моделями
- Запускать независимые задачи параллельно
- Указывать зависимости между задачами
- Передавать воркерам результаты и артефакты зависимых задач
- Загружать ТЗ в Markdown и искать нужный контекст через RAG
- Использовать принятые решения текущего запуска как дополнительный контекст
- Следить за задачами, отвечать на вопросы тимлида и просматривать артефакты в интерфейсе

# Как это работает

1. Пользователь описывает цель, выбирает агента с ролью "тимлид" и воркеров. При необходимости добавляет ТЗ текстом или файлом `.md`.
2. Тимлид получает цель и полное ТЗ, создаёт задачи и указывает зависимости между ними.
3. Планировщик запускает готовые задачи. До трёх независимых задач могут выполняться одновременно, но один агент не выполняет несколько задач одного запуска одновременно.
4. Воркеры получают свои задачи, результаты принятых зависимостей, подходящие фрагменты ТЗ и релевантные решения других задач текущего запуска.
5. Тимлид проверяет результаты по мере готовности и принимает задачи или отправляет их на доработку.
6. Пользователь следит за запуском, задачами и файлами в интерфейсе.

Если тимлиду не хватает информации, он может задать вопрос пользователю. После ответа запуск продолжит работу.

# RAG

ТЗ можно ввести в форме запуска или загрузить файлом `.md` в кодировке UTF-8. Максимальный размер - 128 КБ.

- Markdown разбивается на чанки по заголовкам и абзацам
- Для чанков создаются эмбеддинги через OpenAI-compatible API
- Векторы сохраняются в PostgreSQL с расширением pgvector
- Воркеры получают подходящие фрагменты для своих задач
- Тимлид получает полное ТЗ и релевантные фрагменты при ревью
- После принятия задачи её результат и артефакты индексируются для поиска внутри текущего запуска
- Другие воркеры и тимлид на ревью получают релевантные принятые решения как дополнительный контекст

Запуск без ТЗ может работать без сервера эмбеддингов, но для поиска по памяти принятых задач он необходим.

Память задач индексируется в фоне. Если сервер эмбеддингов недоступен, задача остаётся принятой; состояние индексации и кнопка повтора доступны в её карточке.

# Запуск

## Требования

- Docker и Docker Compose
- API-ключ и модель провайдера с поддержкой OpenAI-compatible Chat Completions API
- LM Studio с загруженной моделью эмбеддингов - для поиска по ТЗ и памяти задач

## Настройка окружения

Создай `.env` в корне проекта и укажи свои значения:

```env
DB_USER=postgres
DB_PASSWORD=your_database_password
POSTGRES_DB=orchestrator

LLM_BASE_URL=https://openrouter.ai/api
LLM_MODEL=provider/model-name
LLM_API_KEY=your_api_key

EMBEDDING_BASE_URL=http://host.docker.internal:1234
EMBEDDING_MODEL=your_embedding_model
EMBEDDING_API_KEY=

MAX_LEAD_STEPS=40
```

`LLM_MODEL` и `LLM_API_KEY` нужно заменить на модель и ключ своего провайдера. При первом запуске на их основе создаётся тимлид. Воркеров можно добавить через раздел **«Агенты»** в интерфейсе, указав их роль, модель, адрес API и ключ.

`EMBEDDING_MODEL` - идентификатор модели эмбеддингов в LM Studio. Проверить доступные модели можно командой:

```powershell
Invoke-RestMethod http://localhost:1234/v1/models
```

`EMBEDDING_BASE_URL=http://host.docker.internal:1234` используется, когда backend работает в Docker, а LM Studio - на Windows или macOS. Для локального запуска backend используй `http://localhost:1234`. `EMBEDDING_API_KEY` нужен только если сервер эмбеддингов требует ключ.

## Docker Compose

Запусти сервисы из корня проекта:

```bash
docker compose up -d --build
```

После запуска доступны:

- Frontend: http://localhost:3000
- Backend API: http://localhost:8080/api/runs
- PostgreSQL: localhost:5433

Для остановки сервисов:

```bash
docker compose down
```

Данные PostgreSQL сохраняются в Docker volume. После изменения `.env` пересоздай нужные сервисы, например:

```bash
docker compose up -d --build backend frontend
```

## Локальный запуск backend

Go-модуль находится в `backend/`. При запуске из этой папки backend читает `.env` из корня проекта, если в `backend/` нет собственного `.env`.

Для подключения к PostgreSQL из Docker в корневом `.env` укажи `DB_HOST=localhost` и `DB_PORT=5433`, затем выполни:

```bash
cd backend
go run ./cmd/api
```

Для локального backend адрес LM Studio указывается как `EMBEDDING_BASE_URL=http://localhost:1234`.

# Проверка

Для запуска тестов локально нужны Go 1.26.1 и Node.js с npm.

Go-тесты:

```bash
cd backend
go test ./...
```

Тесты интерфейса (из корня проекта):

```bash
cd frontend
npm install
npm test -- --watch=false --runInBand
```

Интеграционные Go-тесты с PostgreSQL запускаются при заданной переменной `ORCHESTRATOR_TEST_DSN`. Для них используй отдельную тестовую базу: тесты создают в ней таблицы и записи. Чтобы тестовые пакеты не запускали миграции одновременно, используй `go test -p 1 ./...`.

# Ограничения MVP

- Проект рассчитан на локальный запуск: авторизации и разделения данных пользователей пока нет
- ТЗ и результаты передаются выбранным моделям; при использовании облачного провайдера эти данные отправляются ему
- Полное ТЗ вместе с остальным промптом должно помещаться в контекст модели тимлида
- После перезапуска backend незавершённые запуски автоматически не восстанавливаются
- Тимлид может выполнить до 40 решений на запуск, включая продолжение после ответа пользователя; лимит задаётся через `MAX_LEAD_STEPS`
- Агент создаёт артефакты с содержимым файлов; приложение само не запускает сгенерированный код
